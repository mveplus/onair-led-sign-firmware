How the On-Air sign works

A walk through the system, from the reason it exists down to the code, with live simulations of the firmware's behaviour.

Use ← → or swipe to move, O for an overview. Click the sign.

The idea

When you join a video call, a neon sign outside the room lights up. When the call ends, it goes dark. Nobody has to remember to flip a switch.

  • Detection happens in the browser. The On-Air Meeting Trigger extension notices a meeting tab.
  • Switching happens on a small ESP32-C6 board wired to the sign's power through a MOSFET.
  • Reachability works both at home (direct HTTP on the LAN) and away (through AWS IoT Core).
  • Safety comes first: the sign always powers up OFF, and no cloud secrets ship in the source or the binaries.

    Sign:ON AIR

    Hardware: a low-side MOSFET switch

    The sign and the board share one USB-C 5 V supply. Hover or tap a part.

    Why this circuit

    The ESP32 can't power a sign from a 3.3 V pin. Instead it drives the gate of a logic-level N-channel MOSFET that sits between the sign's negative lead and ground. Gate high: current flows and the sign lights. Gate low: the sign is dark. PWM on the gate gives the "breathing" effect.

    Supported boards: Seeed XIAO ESP32-C6 (default) and DFRobot Beetle ESP32-C6. Both are built in CI.

    Firmware shape: one sketch, a few cooperating ticks

    onair-led-sign-firmware.ino~2300 lines: output, portal, HTTP API, OTA, reset, Wi-Fi
    aws_iot.{h,cpp}MQTT/TLS client, topics, Device Shadow
    aws_provisioning.{h,cpp}Fleet Provisioning by Claim
    partitions.csvcustom 4 MB layout with two OTA slots
    scripts/cloud-bridge/Python Lambda + deploy and test scripts

    No RTOS tasks of its own. HTTP runs in ESPAsyncWebServer's task; everything else is a non-blocking tick called from loop() every ~5 ms.

    loop(): click a line

    1. if (rebootPending …) ESP.restart()
    2. handleSerialStickerCommand()
    3. if (portalMode) dnsServer…; timeout
    4. breathingTick()
    5. handleResetLongPress()
    6. statusLedTick()
    7. wifiSupervisorTick()
    8. awsIotLoop()
    9. delay(5)

    Each tick checks millis() and returns quickly, so one slow subsystem never freezes the others.

      Inside setOutputMode()
      
  
      
    
      // every path ends up here: HTTP, MQTT, BOOT restore
void setOutputMode(int mode) {
  if (mode < MODE_OFF || mode > MODE_BREATHING) mode = MODE_OFF;
  outputMode = mode;
  if (outputMode == MODE_BREATHING) {
    ensurePwmAttached();          // ledcAttach 1 kHz, 10-bit
    breathPhaseStart = millis();
  }
  if (outputMode == MODE_ON)       outputWrite(true);
  else if (outputMode == MODE_OFF) outputWrite(false);
#if ENABLE_AWS_IOT
  awsIotPublishState(outputMode); // state topic + shadow
#endif
}

// breathingTick(): a triangle wave
elapsed = (millis() - breathPhaseStart) % period;
if (elapsed < half) pct = min + span * elapsed / half;
else                pct = max - span * (elapsed - half) / half;
      
    
      
      
        
        
      • One funnel. The local API, the MQTT cmd topic and the BOOT-button restore all call setOutputMode(). That's why every change is reported to the cloud, whichever path caused it.
        • 
        
      • Invalid input fails safe. An unknown mode number becomes OFF.
        • 
        
      • The mode isn't persisted. Breathing timing is saved to NVS; the on/off mode is not. A saved "ON" used to light the sign after a power cut even with no meeting in progress, because MQTT commands never updated the saved value.
        • 
        
      • Polarity aware. If the output is the onboard LED and it's active-low, the PWM duty is inverted.
        • 
      
      
    
      
  
      

      



      
  
      Local HTTP API and authentication
      
  
      
    
      
      
        
        
      • An API token is generated on the first successful Wi-Fi join: 12 hex digits of MAC plus 64 bits from esp_random(). It's shown on the device's web page.
        • 
        
      • ensureApiAuth() accepts the token as X-API-Token, Authorization: Bearer or ?token=, and falls back to HTTP Basic (admin/esp32c6 until you change it).
        • 
        
      • mDNS advertises http://<hostname>.local/.
        • 
        
      • Reboots from HTTP handlers are deferred (scheduleReboot()) so the response, or a 303 redirect, reaches the browser first.

      The 5 s reset keeps the sticker (mfg) and the AWS identity (aws_iot). The 15 s reset runs nvs_flash_erase(): every namespace, including the per-device private key, is gone, as if the board were freshly flashed.

      Staying online without a human
      
  
      The sign sits on a shelf for months. Drag the slider to see what the firmware does as an outage gets longer.
      
  
      
    
      
      
      
      15 min
      
      
      
    
      
    
      
      
        
        
      1. Layer 1: tell the core to try harder. setAutoReconnect(true), setSleep(false) (mains-powered, so modem power-save that misses beacons buys nothing), and persistent(false) so reconnects don't wear out NVS.
        2. 
        
      2. Layer 2: active supervisor. Every 10 s while down, wifiSupervisorTick() runs WiFi.disconnect() + WiFi.begin() again. That revives the supplicant even after the core's own retries have given up.
        3. 
        
      3. Layer 3: reboot. After 15 minutes offline, ESP.restart() clears any stuck Wi-Fi/lwIP state.
        4. 
        
      4. Portal timeout. A setup AP nobody uses reboots after 10 minutes and tries the saved network again, which covers a router that was simply down at boot.
        5. 
      
      
    
      
  
      

      



      
  
      AWS IoT Core: optional, credentials only at runtime
      
  
      
    
      
      
        
        
      • The firmware reads {endpoint, thing, root_ca, cert, key} from the aws_iot NVS namespace. If any of them is missing, the module stays idle.
        • 
        
      • The only certificate compiled in is the public Amazon Root CA 1, and it can be overridden at runtime.
        • 
        
      • NTP before TLS. The chip has no RTC; at the 1970 epoch every certificate looks "not yet valid". It waits up to 8 s for pool.ntp.org.
        • 
        
      • Mutual TLS to port 8883, 60 s keep-alive, reconnect every 5 s on failure. rc = -4 means TLS succeeded but AWS dropped the link: wrong region or IoT policy.
        • 
        
      • Build with ENABLE_AWS_IOT=0 for a LAN-only firmware without the module.
        •

      The cloud bridge: one Lambda, two verbs
      
  
      
    
      # scripts/cloud-bridge/lambda_function.py
def lambda_handler(event, _ctx):
    if method == "OPTIONS": return 204          # CORS preflight
    if auth != f"Bearer {SHARED_TOKEN}": return 401
    return handle_get(event) if method == "GET" \
      else handle_post(event)

# POST {"thing": "onair-office", "mode": 1}
iot.publish(topic=f"onair/{thing}/cmd",
            qos=0, payload=json.dumps({"mode": mode}))

# GET ?thing=onair-office
doc  = iot.get_thing_shadow(thingName=thing)
mode = parse_reported_mode(doc)   # mode → output_mode → state
      
    
      
      
        
        
      • POST sends a command. The device doesn't have to be reachable from the internet, because it keeps an outbound MQTT connection open.
        • 
        
      • GET returns the last reported state from the Device Shadow. The extension uses it to check the real state when the LAN is out of reach.
        • 
        
      • Shared bearer token, plus an optional ALLOWED_THINGS allowlist (403 otherwise).
        • 
        
      • parse_reported_mode() uses the same mapping as the firmware and the extension, so 0/1/2 and "off"/"on"/"breathing" agree everywhere.
        • 
        
      • Unit tests in test_lambda.py; validate-shadow.sh checks the whole path without hardware.
        •

      Why count lines starting with "MII"?
      
      
      Every real X.509 cert or private key is base64 of an ASN.1 SEQUENCE (first byte 0x30), so its body starts with MII. HTML placeholders and mbedTLS marker strings have no body. Exactly one hit is allowed: Amazon Root CA 1.
      
      
      
      
      
      
        
        
        
      
      
    
      
  
      

      



      
  
      The ideas behind it
      
  
      
    
      Fail dark
      Pull-down resistor, OFF in setup(), mode not saved. A power blip never lights the sign by itself.
      
    
      Local first, cloud optional
      The LAN API works with no account. AWS is a runtime opt-in, and ENABLE_AWS_IOT=0 removes it entirely.
      
    
      No secrets in the artifact
      Credentials live in NVS. CI checks every binary for endpoints and PEM bodies.
      
    
      One funnel, always reported
      Every change goes through setOutputMode(), which publishes state and shadow, so the extension can correct drift.
      
    
      Self-healing
      Wi-Fi supervisor, 15-minute reboot, portal timeout, MQTT backoff. No one has to power-cycle it.
      
    
      Physical recovery
      BOOT holds and serial commands reset it even when the network is gone. A 15 s hold leaves no secrets behind.
      
    
      The sticker survives
      Separate mfg namespace: a factory reset keeps the printed QR valid, and stk_lock hides it after deployment.
      
    
      Non-blocking ticks
      A cooperative loop() keeps breathing, reset feedback, Wi-Fi and MQTT running side by side.
